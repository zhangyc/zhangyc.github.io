Agentic 时代，开发范式正在从“写代码”转向“MCP + Skill”

Created2026-03-16|Updated2026-03-16|AI 工程化
|Post Views:

如果今天还把 AI 编程理解成“更强的代码补全”，那大概率低估了这轮变化的深度。真正的变化不是生成速度变快了，而是软件生产的基本组织方式正在改变：工程师开始越来越少地直接实现细节，越来越多地为 agent 搭建能力、知识和流程。

我越来越强烈地感受到：开发的基本单位变了

过去十几年，软件开发的基本单位一直很稳定：

  • 写函数
  • 抽象模块
  • 封装 SDK
  • 搭框架脚手架
  • 沉淀内部平台

无论技术栈怎么变，这套思路都成立。因为默认前提没有变：代码是人直接生产的，工具只是辅助人提高效率。

但在 Agentic 时代，这个前提正在失效。

今天越来越多时候，真正直接产出代码的，不再是工程师本人，而是像 Claude Code 这样的代理型 AI。工程师的角色开始从“亲手实现每个细节”，转向“给代理分配任务、提供上下文、约束输出质量、校验最终结果”。

这不是简单的“AI 帮我补全代码”，而是开发范式层面的迁移：

从面向代码实现，转向面向能力编排。

而在这个新范式下，我认为最关键的两个构件就是：

  • MCP：给代理接上外部工具和系统
  • Skill：给代理注入领域知识和执行规范

如果说传统工程化是在构建“人如何更快写代码”的体系，那么 MCP + Skill 构建的是“AI 如何稳定地产出正确代码”的体系。

这篇文章我想结合 Claude Code，聊聊这件事为什么会发生，以及团队应该如何理解这场迁移。

传统开发范式，优化的是“人”

回头看我们熟悉的工程实践，几乎都在优化同一个目标：降低人写代码的成本。

例如：

  • 组件库，减少重复 UI 开发
  • 脚手架，减少项目初始化成本
  • SDK，屏蔽底层协议细节
  • CI/CD，减少人工发布步骤
  • 规范和 Code Review，降低多人协作的质量波动

这些东西当然依旧重要，但它们的设计对象本质上都是人。默认假设是：

  1. 人理解需求
  2. 人查文档
  3. 人决定调用哪个 API
  4. 人把代码写出来
  5. 工具在旁边帮一点忙

这就是传统 IDE 时代的工作流。

但当 Claude Code 这类 agent 真正参与到开发主流程之后，工作流变成了另一种形式：

  1. 人提出目标
  2. Agent 自己读代码库、查文档、调用工具
  3. Agent 组合上下文后生成方案和代码
  4. 人负责确认方向、验收结果、做关键决策

在这个新流程里，真正决定效率上限的，不再只是“你有没有封装好函数库”，而是：

  • Agent 能不能拿到需要的上下文
  • Agent 能不能调用需要的外部能力
  • Agent 知不知道你团队的规则、约束和偏好
  • Agent 生成之后，能不能尽量一次就对

这就是为什么单纯给 AI 一个大模型还不够。你必须继续做工程化，只是工程化对象从“人”变成了“代理”。

Agentic 开发里，代码不再是唯一资产

在传统范式里，团队最重要的资产通常是：

  • 代码库
  • 文档库
  • 组件库
  • 基础设施

而在 Agentic 范式里，我认为还要新增一类核心资产：

  • 可被代理调用的能力
  • 可被代理理解的知识
  • 可被代理复用的工作流

对应到 Claude Code 里，分别就是：

  • MCP Server：把数据库、Figma、接口平台、日志系统、知识库接进来
  • Skill：把框架规范、架构约束、团队约定、私有库用法写成可触发的知识包
  • Prompt / Instructions：把任务分解方式、输出格式、交付标准固定下来

也就是说，未来团队沉淀的不只是“源码”，还包括：

  • AI 能调用什么
  • AI 在什么场景下应该怎么做
  • AI 做事时必须遵守哪些规则

从这个角度看，MCP 和 Skill 不是“Claude Code 的两个功能点”，而是 Agentic 工程化的两条主线。

MCP 解决的是“AI 能做什么”

MCP，Model Context Protocol，本质上是在解决一个长期存在的问题：怎么让模型以标准方式访问外部世界。

没有 MCP 之前，AI 的工具调用高度平台私有化。你为一个平台写的 function calling，大概率不能直接迁移到另一个平台。工具和模型强绑定，工程复用性很差。

MCP 把这一层标准化之后，事情就简单很多了：

  • 你实现一个 MCP Server
  • Claude Code 之类的客户端接进来
  • Agent 就能按统一协议调用你的工具

在开发场景里，这件事非常关键，因为真实的软件开发从来不是只靠本地代码库完成的。Agent 往往还需要：

  • 读取设计稿
  • 查询后端接口定义
  • 看日志和监控
  • 访问内部知识库
  • 读取数据库 schema
  • 获取项目任务单或 PR 信息

这些都不是模型参数里自带的知识，必须实时获取。

所以 MCP 的价值不只是“多一个工具接口”，而是让 Agent 真正具备进入生产环境上下文的入口。

你可以把它理解为：MCP 负责把 AI 从聊天窗口里放出来。

Skill 解决的是“AI 应该怎么做”

但仅有 MCP 还不够。

Agent 即使拿到了上下文，也不代表它会按你的方式工作。它仍然可能：

  • 用错架构模式
  • 生成不符合团队风格的代码
  • 误用私有库
  • 忽略一些你们默认不允许的实践
  • 写出“看起来能跑，但不符合工程约束”的实现

这时候需要的是 Skill。

在 Claude Code 里，Skill 更像是一份会被自动激活的“领域作战手册”。它告诉 Agent：

  • 什么时候应该使用这份知识
  • 这个技术栈有哪些核心概念
  • 应该遵守哪些规则
  • 不应该采用哪些写法
  • 输出最好长成什么样

如果说 MCP 是扩展能力边界，那么 Skill 就是在收敛输出质量。

我越来越觉得，Skill 的真正价值不是“教 AI 知识”，而是把团队隐性经验显式化。

过去这些经验散落在：

  • 老同事脑子里
  • Code Review 评论里
  • Wiki 某个角落里
  • 已经写过的项目代码里

现在你需要把它整理成 Agent 可以直接消费的结构化知识。这样 AI 每次执行任务时，不是“临场猜测”，而是在复用团队已经达成共识的做法。

换句话说，Skill 不是让 AI 变聪明一点，而是让它少犯那些你们已经犯过无数次、并且本不该再犯的错误。

以 Claude Code 为例，一个完整任务到底靠什么跑起来

如果只看 Claude Code 的表面体验，你会觉得它像一个更强的命令行助手。但真正让它和传统补全式 AI 拉开差距的，是它开始具备“自主完成任务”的能力。

一个典型的请求可能长这样：

根据 Figma 设计稿，实现设置页；遵循我们项目的 Flutter 分层规范；表单提交走现有的 profile API；同时补上测试。

这句话对人类工程师来说很好理解，但对 AI 来说，里面藏着大量前提条件：

  • Figma 设计稿在哪
  • Flutter 项目规范是什么
  • profile API 长什么样
  • 测试模板怎么写

Claude Code 如果要稳定完成这个任务，背后至少需要三层支撑。

1. 代码库上下文

它需要能读当前项目，理解目录结构、已有模式、现有实现。

2. MCP 提供的外部能力

比如：

  • Figma MCP：读取设计稿和图片资源
  • API 平台 MCP：读取接口定义
  • 文档系统 MCP：拉取架构说明

3. Skill 提供的领域约束

比如一个 Flutter Skill 里明确规定：

  • 页面状态怎么组织
  • 副作用怎么处理
  • Service / Repository 如何分层
  • 表单校验应该放在哪里
  • 测试至少覆盖哪些行为

这时候 Claude Code 才不是“帮你写一段代码”，而是在执行一个具备上下文、能力和规范的完整任务。

这也是为什么我觉得，未来好的工程师不只是会写代码，还要会设计“让 agent 成功完成任务的环境”。

一个最小可行的 Claude Code 落地方式

这件事不一定要从“大而全平台建设”开始。对大部分团队来说，一个足够实用的起点通常只有三步。

第一步：先让 Claude Code 读懂项目

把这些最基础的信息写清楚：

  • 项目结构
  • 常用命令
  • 代码规范
  • 关键模块边界

这一步的目标不是完美，而是避免 agent 每次都从猜目录、猜命令开始。

第二步：选一个高频场景写 Skill

不要一上来覆盖整个技术栈。先挑一个最容易反复返工的场景，例如：

  • Flutter 页面开发
  • 后端接口接入
  • 状态管理代码生成
  • 单元测试补全

只要这个场景满足“高频、稳定、容易写错”，就值得先做成 Skill。

第三步：给它补一个最关键的 MCP

通常第一个最值得接入的，不是最复杂的系统，而是最常阻塞 agent 的那个外部信息源，比如：

  • 设计稿
  • 接口文档
  • 内部知识库

这样做完之后，Claude Code 的工作流就会从“只能基于当前目录猜”，变成“能基于项目上下文、外部信息和团队规范共同完成任务”。

这已经不是小修小补，而是工作方式发生变化的起点。

为什么说这是从“编码”转向“编排”

过去一个资深工程师的价值，很多时候体现在：

  • 抽象能力强
  • API 设计好
  • 能迅速定位问题
  • 熟悉系统边界

这些能力今天依旧重要，但表达形式会发生变化。

在 Agentic 时代，资深工程师会越来越多地把这些能力沉淀成三类资产。

第一类：能力接口

把内部系统包装成 MCP Server，让 agent 能访问。

这件事本质上是在做 AI 时代的内部平台。以前你给人封装 SDK，现在你给 agent 暴露工具。

第二类：知识约束

把团队共识、框架规范、私有库模式写成 Skill。

以前新人要靠口口相传、读历史代码、挨 review 才学会；现在这些东西可以直接前置到生成阶段。

第三类：工作流模板

把高频任务拆成稳定流程，例如：

  • 读 PRD
  • 拉设计稿
  • 查接口
  • 生成骨架
  • 运行测试
  • 按规则修复问题

以前这是一个高级工程师在脑中执行的 checklist，现在可以逐渐变成 agent 的执行路径。

所以我会把这场迁移总结成一句话：

传统开发是在生产代码，Agentic 开发是在生产“能持续产出代码的系统”。

一个很现实的判断：以后团队竞争力，取决于“喂给 AI 的体系”

很多人讨论 AI 编程时，关注点还停留在：

  • 哪个模型更强
  • 哪个 IDE 更顺手
  • 哪个 Agent 响应更快

这些当然重要，但我认为它们越来越像基础设施红利，差距会被迅速抹平。

真正会拉开团队差距的，是你有没有系统化沉淀下面这些东西：

  • 你的 MCP 接了哪些内部系统
  • 你的 Skill 覆盖了哪些关键场景
  • 你的 prompt / instructions 有没有把任务边界定义清楚
  • 你的代码库是否足够规范，便于 agent 理解和延续模式

换句话说，未来工程团队的护城河，可能不只是代码本身，而是：

一套让 AI 可以稳定、高质量参与生产的软件工厂。

同样使用 Claude Code，有的团队只能拿它写几个 util；有的团队却已经可以让它参与页面开发、接口联调、测试补全、文档生成，差别往往不在模型，而在配套工程化水平。

以 Claude Code 为例，团队应该沉淀什么

如果你已经接受“开发范式正在迁移”这个前提，那么接下来最实际的问题就是：到底该沉淀什么？

我自己的答案是四层。

第一层：项目说明要对 agent 友好

例如：

  • 项目结构说明
  • 启动、测试、构建命令
  • 关键目录职责
  • 代码风格和提交约束

这些信息过去写给人看，现在也必须写给 agent 看。

第二层：把外部系统能力 MCP 化

优先级通常最高的是这些：

  • 设计稿
  • 接口文档
  • 日志 / 监控
  • 任务系统
  • 内部知识库

原则很简单：凡是工程师在开发时经常要打开的系统，都值得评估是否提供给 agent。

第三层：把高价值知识 Skill 化

什么最值得写成 Skill？

  • 私有框架 / 私有库
  • 复杂业务模块的固定模式
  • 团队有强约束的架构规范
  • 容易被 AI 写错但又频繁出现的场景

不是所有知识都值得做 Skill。最适合 Skill 的，是那些“高频、稳定、隐性、犯错代价高”的知识。

第四层：把高频任务流程化

例如：

  • 新页面开发流程
  • 新接口接入流程
  • 缺陷修复流程
  • 重构和回归验证流程

当流程足够清晰时，Claude Code 这种 agent 的产出稳定性会明显提高。

不要误解 Skill：它不是“提示词收藏夹”

很多人第一次接触 Skill，会把它理解成“更长一点的 prompt 模板”。这理解不算全错，但会低估它的价值。

我更倾向于把 Skill 看成三件事的结合：

  • 可触发的知识包
  • 可执行的约束说明
  • 可复用的领域工作协议

一个好的 Skill，不应该只是写几句“请按照最佳实践生成代码”。这种话几乎没有约束力。

真正有用的 Skill，通常会包含：

  • 明确的触发语义
  • 核心概念说明
  • 推荐模式
  • 禁止模式
  • 代码示例
  • 输出要求

它像是一份给 AI 的团队入职手册，而且是“遇到相关任务自动发给它看”的那种。

这也是为什么在 Claude Code 的实践里，我认为 Skill 不是可有可无的小插件，而是把工程经验产品化的关键媒介。

传统封装不会消失，但会后移一层

这里有一个容易被误解的地方：强调 MCP 和 Skill，并不意味着函数、SDK、组件库这些传统工程资产不重要了。

不是这样的。

它们依旧重要，只是它们的位置变了。

以前，抽象这些东西的主要目的，是为了让人更高效地调用。

现在，除了让人调用，你还要考虑能否让 agent 更容易理解、发现和正确使用。

所以未来好的工程资产会同时满足两件事：

  1. 对人类开发者友好
  2. 对代理型 AI 也友好

举个最简单的例子：

  • 一个 API SDK 仍然要设计得清晰
  • 但你还需要一个 Skill 告诉 Claude Code 在什么场景该怎么用它
  • 如果这个 SDK 依赖外部信息，你可能还要提供 MCP 工具配套读取上下文

也就是说，传统封装没有消失，而是被纳入了更大的 Agentic 生产体系里。

我理解中的迁移路径

如果一个团队今天想开始做这件事，不需要一上来就做得很重。我建议按下面的顺序走：

阶段一：先让 Claude Code 读懂项目

先把项目说明、目录结构、常用命令、约束规则写清楚。

阶段二：把最常用的知识做成 Skill

优先处理那些你已经重复讲过很多遍、Review 里反复提的问题。

阶段三：把最常用的外部系统做成 MCP

让 agent 不要总是卡在“缺上下文”这一步。

阶段四：围绕高频任务做端到端工作流

让 agent 从“能写一段代码”，升级成“能完成一类任务”。

比如在 Claude Code 里，一个已经比较顺的任务链路，往往会变成这样：

  1. 读取项目 instructions，确认目录结构和约束
  2. 调用 MCP 拉取设计稿、接口或文档
  3. 激活对应 Skill，按团队规范生成代码
  4. 运行测试或构建命令
  5. 根据结果自动修正，再交给人做最终验收

这条路径的关键不在炫技，而在务实。每做一层，你都应该看到明确收益：

  • 返工变少
  • 解释成本变少
  • Review 成本变少
  • 首次产出可用率变高

只要这几个指标在改善，说明方向就是对的。

小结

我现在越来越不把 Claude Code 只看成一个“更强的 AI 编程工具”。

在我眼里，它更像是 Agentic 开发时代的一个缩影：代理开始真正进入工程生产流程，而我们的开发范式也必须跟着变化。

过去我们优化的是“如何让人更高效地写代码”；现在我们要优化的是“如何让 agent 稳定地完成开发任务”。

在这个迁移过程中：

  • MCP 负责连接能力
  • Skill 负责注入知识
  • Instructions / Workflow 负责约束执行方式

它们共同组成的，不是某个产品的附属功能，而是一种新的软件工程方法。

真正值得团队投入的，也不是“让 AI 看起来很聪明”，而是让它在你的工程环境里稳定、低返工、可复用地完成任务。

如果说过去高级工程师最重要的工作，是抽象代码；那么未来越来越重要的工作，可能是抽象可供 agent 使用的能力、知识与流程。

这就是我理解的，传统开发范式向 MCP + Skill 转变的本质。
